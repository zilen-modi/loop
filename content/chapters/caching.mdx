A cache is a copy of data kept somewhere faster than where it lives. Caches are the most common answer in system design, because most systems read far more than they write. They're also behind some of the most common outages: stale prices, stampedes and hot keys. This chapter covers where caches go, how reads and writes keep them in step with the database, and how to keep the cache from turning on you.

## Where caches live

From closest to the user to furthest:

- **The browser**, controlled by HTTP headers such as `Cache-Control` and `ETag`.
- **A CDN**: copies of responses at the edge, close to users. Good for anything public and the same for everyone.
- **The app server's memory.** Fastest of all, but each server has its own copy, so they can disagree.
- **A shared cache** such as Redis or Memcached: one copy for every app server, about a millisecond away.

Each layer cuts load on the next one in. The cost is another copy that can be out of date.

## Reading: cache-aside

The default pattern is <Term id="cache-aside">cache-aside</Term>. The app checks the cache; on a miss it reads the database and puts the result in the cache for next time. The cache only ever holds what's actually asked for, and if the cache goes down, the app still works (slowly). The URL-shortener lab uses exactly this.

<Checkpoint id="cache-average" />

**Read-through** is the same idea with the cache doing the fetching itself (the app only talks to the cache). It's tidier code, but it ties the cache to the database.

## Writing: keep the copies honest

When data changes, the cached copy is wrong until something fixes it. Four strategies:

- **Invalidate on write (cache-aside's partner).** Write to the database, then **delete** the cache entry, and let the next read refill it. Deleting rather than updating matters. If two writers race, "update the cache" can leave the older value in it for good, while a delete just causes one extra miss.
- **Write-through.** Write to the cache and the database together. Reads are always fresh, but every write pays for both.
- **Write-back (write-behind).** Write to the cache only, and flush to the database later in batches. Very fast writes, but a cache crash loses data. Fine for counters and view counts, not for payments.
- **Write-around.** Write only to the database and let entries expire. Simple, and good for data that's written once and rarely read again.

And a safety net for all of them: a **TTL**. Even if an invalidation is lost, a stale entry dies after its time-to-live.

## When the cache turns on you

A **stampede** (or thundering herd) happens when a popular entry expires and every request that misses goes to the database at the same time, all asking for the same thing. A **synchronised expiry** is the same problem spread across many keys: everything cached at once expires at once, as in the story. Play with both:

The fixes:

- **Request coalescing** (single-flight). The first miss for a key fetches it; every other miss for the same key waits for that one result. Facebook's memcache does this with "leases".
- **Jittered TTLs.** Add a little randomness to each expiry so they spread out.

<Checkpoint id="cache-jitter" />

- **Refresh ahead.** Refetch a hot entry shortly *before* it expires, in the background.
- **Serve stale while revalidating.** Return the old value for a moment while one request refreshes it.

A **hot key** is the other trap. One celebrity restaurant's menu can get more traffic than a single cache node can serve. Keep copies of the hottest keys in each app server's memory for a few seconds, or replicate them across several cache nodes.

## Eviction

A cache is smaller than the data, so something has to go. Least recently used (LRU) is the usual default. Least frequently used (LFU) protects popular items from bursts of one-off reads. Building both in O(1) is a classic build: see the LRU and LFU chapter in the LLD book.

## In interviews

What you'll be asked next:

- "Where would you cache?" Name the layer, say what's cached and for how long, and say how it's invalidated.
- "How stale can this be?" A menu can be a minute old; a wallet balance can't be cached at all, or only with write-through and short TTLs.
- "What happens when the cache goes down?" Cache-aside degrades to slow, but if the database can't take the full load, that's an outage. Size for it, or protect the database with rate limits.
- "A key is too hot." Local in-memory copies, replicas of the key, or splitting the key.

Traps that cost people the round:

- Updating the cache on write instead of deleting it, and the race that leaves stale data.
- No TTL, so a lost invalidation lasts forever.
- Caching per-user data in a CDN.
- Forgetting the stampede when an interviewer says "hot key" or "flash sale".
