<Story when="Saturday, 8:15 pm">
The push provider has a bad five minutes during Saturday dinner. Tiffin's ordering service calls it directly when an order is accepted, so for five minutes accepting an order takes thirty seconds and then fails. Customers retry. When the provider comes back, half of them get three "Order accepted!" notifications for one order.
</Story>

A notification system looks like plumbing: take a message, hand it to a provider. The interview is about everything that goes wrong between those two steps. Third parties are slow and unreliable, traffic comes in bursts, retries create duplicates, and customers have opinions about what they want to hear.

## Requirements and numbers

- Internal services call one API: "send template X to customer Y with this data". They get an id back immediately.
- Each notification is delivered once, unless the customer has turned that kind off.
- Failures are retried; messages that keep failing are set aside for a person to look at.

At dinner peak that's 20,000 notifications a second. The provider takes about 200 ms per send, so roughly 4,000 sends are in flight at any moment. A five-minute outage means millions of messages that need somewhere to wait.

## Accepting is not delivering

The story's mistake was making callers wait for the provider. Split the work in two:

1. **Accept.** The API validates the request, writes it to a durable <Term id="message-queue">message queue</Term>, and answers with an id in a few milliseconds.
2. **Deliver.** A pool of workers reads the queue, checks the customer's preferences, sends to the provider, and acknowledges the queue message only after the send succeeds.

Now provider slowness and outages show up as a growing queue, not as slow orders. The queue also smooths bursts: a promo blast becomes a queue that drains at whatever rate the workers and the provider can manage.

## Retries without making things worse

Retrying is obvious; how you retry is the interview. Compare three policies during an outage:

<RetryLab />

- **Drop failures:** simple, and every outage loses millions of notifications.
- **Retry at once:** workers spin on failing sends, hammering a provider that's trying to recover. Fresh messages queue up behind the retries.
- **Exponential backoff with jitter:** wait 1 s, 2 s, 4 s and so on, plus a random amount, so retries from thousands of messages don't arrive together. After a fixed number of attempts, move the message to a **dead-letter queue** and alert, so one poisoned message can't loop forever.

## Exactly once is a promise you can't keep (but you can fake it)

Queues deliver *at least once*: a worker that crashes after sending, but before acknowledging, will see the same message again. And a send that timed out may still have reached the phone. So duplicates are normal, and the fix is an <Term id="idempotency">idempotency key</Term>. Each notification gets an id when it's accepted. Before sending, the worker records the id in a fast store such as a cache, and if it's already there, it skips the send. Keep ids for a window long enough to cover retries (hours, not forever).

## Preferences and priorities

Every send checks the customer's preferences: which kinds they want, quiet hours, a cap on promotions. That's a small, read-heavy lookup, ideal for a key-value store with a cache in front.

Priorities matter more than they first seem. A one-time password stuck behind six million promotional messages is a broken login. Use separate queues (or a priority field the workers respect) so OTPs and order updates go first.

## In interviews

What you'll usually be asked next:

- "Add SMS and email." One queue per channel, each with its own workers, provider and rate limits, so a slow email provider can't hold up push.
- "Track delivery status." Workers write a status (sent, delivered, failed) per notification id; support can look it up.
- "A promo blast to 40 million customers." Fan out in batches through a low-priority queue, rate-limited so it never starves order updates.
- "Templates and localisation." Render at send time from a template id and data, in the customer's language.

Traps that cost people the round:

- Calling the provider synchronously from the request path.
- Retries without backoff, or without a dead-letter queue.
- No answer for duplicates, or claiming exactly-once delivery.
- One queue for everything, so OTPs wait behind promotions.
