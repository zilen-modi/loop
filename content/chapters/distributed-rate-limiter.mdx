<Story when="Monday, 11 am">
The partner API's rate limiter worked perfectly in testing: 100 calls a minute per partner, enforced by a token bucket in the gateway's memory. In production there are eight gateways behind a load balancer. One partner's runaway script gets 800 calls a minute through, and the on-call engineer spends an hour finding out why.
</Story>

The LLD book built a rate limiter for one machine. This chapter is about the same limiter spread across a fleet. A limit is about a *partner*, but the work is spread across *machines*, so the question becomes: where does the count live, and what does that cost each call?

## Requirements and numbers

- Every API call is checked against its partner's limit before it reaches the API servers. Over the limit means a 429 with a retry time.
- Limits are accurate to within about 10% however many gateways are running, and the check adds at most a couple of milliseconds.
- A counter-store outage mustn't take the API down. No single partner can swamp a machine.

The numbers: 30,000 calls a second at peak from 50,000 partners. The biggest, a national chain, sends about 30% of them. The state is tiny: 50,000 partners × about 100 bytes is roughly 5 MB. Memory isn't the hard part; agreement between machines is.

## Where does the count live?

<Checkpoint id="drl-local" />

There are three answers, each with a cost.

**Each gateway on its own.** Nothing shared, no extra hop. But a partner spread over N gateways is counted N times separately, so it can get N times its limit through. You can make local counts exact by sending each partner to the same gateway (consistent hashing on the partner id), but then the chain's 9,000 calls a second land on one machine.

**A shared counter store.** A token bucket per partner in an in-memory store such as Redis, updated on every call by a short atomic script: refill, check, take. It's exact, and costs one round trip (well under a millisecond) per call. The store must be in memory: a disk-backed database adds milliseconds and can't take 30,000 writes a second on one primary.

<Checkpoint id="drl-nodes" />

**Local counts, synced.** Each gateway counts in memory and pushes its counts to the shared store every 100 ms or so. There's no hop on the call path, and it's accurate to within whatever arrives in one sync interval. It's more to build, and more to explain.

## When the store is down

A shared counter is a new dependency, so decide what happens without it. This is <Term id="fail-open">fail open or fail closed</Term>:

- **Fail open:** let calls through, unchecked, until the store is back, and alert. The API stays up; limits pause.
- **Fail closed:** refuse calls. Limits always hold, but a cache outage becomes an API outage.

Most public APIs fail open, because a few minutes without limits is cheaper than refusing every customer. Systems that limit to protect something fragile downstream (a payment provider with strict quotas, say) may fail closed. Either is a fine answer if you say why.

## Spreading the load

Round robin spreads every partner across every gateway, so even the chain's 9,000 calls a second are shared among six machines. Pair it with a shared or synced counter, and accuracy doesn't depend on where calls land.

## In interviews

What you'll usually be asked next:

- "Limits per endpoint too." Check a second bucket keyed by partner and endpoint; take from both only if both allow it.
- "Multi-region." One global limit needs cross-region coordination (slow), so most systems give each region a share of the limit, or accept regional limits.
- "Tell the client when to retry." Return Retry-After and the remaining quota in headers.
- "Protect a struggling downstream service." That's load shedding: drop or queue low-priority work when latency rises, whoever the caller is.

Traps that cost people the round:

- Local token buckets behind a round-robin load balancer, with no mention of the N× problem.
- Counters in the main SQL database.
- No answer to "what if Redis is down?"
- Sticky routing by partner without noticing the biggest partner's load.
